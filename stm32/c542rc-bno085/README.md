# c542rc-bno085 — NUCLEO-C542RC BNO085 → Classic CAN

`stm32-f303k8` のCAN仕様を維持したSTM32C542RCT6 / HAL2版。
CubeMX2 1.2.0でNUCLEO-C542RCからプロジェクトを作成し、SPI1、FDCAN1、USART2、GPIOを設定した。
既存のF303版は変更していない。

プロジェクトは `sandbox/stm32-c542rc` から `stm32/c542rc-bno085` へ移動済み。
過去の受信ログ・検証結果ファイル・ビルド生成物は整理のため削除した。
以下の実機検証結果は当時の記録の要約であり、生ログは同梱していない。
ソース・設定・テスト・収録ツールとライセンスは保持している。

## CANフレーム仕様（変更なし）

- Classic CAN、標準ID `0x100`、データフレーム、DLC 8、1 Mbps、BRSなし。
- 加速度と校正済み角速度のレポート要求周期はそれぞれ5,000 µs。
- CAN送信要求の最短間隔は5 ms。前回の送信受付後に両レポートが更新され、未完了の送信がないときに送信する。
- 自動再送は無効（DAR）。各データを1回だけ送信試行し、ACK欠落・通信エラー・調停負けで未送信となった場合も同じデータは再送せず、次の周期で最新値へ進む。ACK検査とCANのエラー管理は有効で、受信保証や厳密な5 ms周期の保証はない。
- 最新の加速度・角速度を組み合わせる。計測時刻を一致させる処理はない。
- `bno085_can.dbc` と `protocols/bno085_can.{c,h}` はF303版とバイト単位で同一。
- タイムスタンプ、精度ステータス、新しい診断フレームは追加していない。

| バイト | 信号 | 型 | 物理値 |
|---|---|---|---|
| 0–1 | Accel_X | int16、little endian | raw / 256 m/s² |
| 2–3 | Accel_Y | int16、little endian | raw / 256 m/s² |
| 4 | Accel_Seq | uint8 | センサの連番 |
| 5–6 | Gyro_Z | int16、little endian | raw / 512 rad/s |
| 7 | Gyro_Seq | uint8 | センサの連番 |

FDCANのkernel clockは144 MHz、分周1、nominal prescaler 1、TSEG1=125、TSEG2=18、SJW=1。
`144 MHz / (1 + 125 + 18) = 1 Mbps`、sample point 87.5%。
HAL2の送信APIが標準IDをシフトするため、アプリは `0x100` をそのまま渡す。

## 配線

| BNO085信号 | STM32ピン | 説明 |
|---|---|---|
| H_INTN | PA0 | Active LOW、EXTI0で時刻記録・起床。レベル確認も併用 |
| RESET | PA1 | Active LOW出力、初期HIGH |
| PS0 / WAKE | PB0 | 初期HIGH。ホスト送信時の起床制御 |
| CS | PA4 | Active LOW出力、初期HIGH |
| SCK | PA5 | D13 / SCK、SPI1 SCK、AF5 |
| MISO | PA6 | SPI1 MISO、AF5 |
| MOSI | PA7 | SPI1 MOSI、AF5 |
| PS1 | HIGH | 使用モジュールのSPIモード設定を確認して接続 |
| GND | GND | 共通GND |

電源は使用するBNO085モジュールの仕様に合わせる。GPIO信号は3.3V系。
SPI1のハードウェア通信を使用し、SCK=PA5（D13）、MISO=PA6（D12）、MOSI=PA7（D11）の標準SPI端子に接続する。
初版のSCK=PB7（D14）からPA5へ変更したため、初版の配線を使用している場合はSCK線をD13へ移す。
PA5は基板LED LD1回路と共有されるため、LED専用GPIOとして操作しない。信号品質は実機で確認する。
WAKEはF303版のPA3からPB0（A3）へ変更し、PA3のST-LINK VCPを避けている。
その他のArduino端子表記はINT=A0、RESET=A1、CS=A2。CS・RESET・WAKEのみGPIO出力で制御する。

| 基板内接続 | STM32ピン | 設定 |
|---|---|---|
| CAN RX | PB8 | FDCAN1 RX、AF9 |
| CAN TX | PB9 | FDCAN1 TX、AF9 |
| CAN transceiver STBY | PE2 | 出力LOW（通常動作） |
| ST-LINK VCP TX / RX | PA2 / PA3 | USART2、115200 bps、8N1 |

CANバスは基板内MCP2562FDを介して接続する。既定のSB32/STBY、SB34/TX、SB36/RXの接続を使用する。
配線・電源・終端は実基板のリビジョンと照合する。
根拠：[ST公式C542RC回路図](https://www.st.com/resource/en/schematic_pack/mb2213-c542rc-b02-schematic.pdf)、
[C542 alternate function表](https://www.st.com/content/st_com/en/technical-documents/stm32c542cc_asset/chunk-009-topic-stm32c5xx-db-ds-alternate-functions.html)。

## 実装

- SYSCLK/HCLK/PCLK: HSE 24 MHz → PSIS 144 MHz。
- SPI: Mode 3、8 bit、MSB first、144 MHz / 64 = 2.25 MHz、ソフトウェアCS。
- HAL2の非同期SPI Tx/Rx DMAを使用する。SH-2のreadはDMA完了まで0を返し、その間メイン処理を進める。DMA専用バッファを使い、呼出元バッファの寿命に依存しない。
- SHTPヘッダ4バイトをDMAで読み、CSをLOWに保ったまま本文へ切り替える。上限1024バイト。送信時も受信ヘッダを確認し、送受信の長い方までクロックを送り、同時受信した応答をSH-2へ渡す。
- DMAのヘッダ／本文間でもSPIの端子状態を保持する（Master Keep IO State）。完了はDMA転送完了だけでなくSPI EOT割り込みを経由する。
- BNOのRESET解除後は実機で確認した100 msの待ち時間を置き、その後INTのLOWを確認する。100 msは公式仕様の保証値ではない。PS0は最初のINTまでHIGHを維持する。
- SH-2コールバックごとに加速度と角速度を別々に保持する。同一パケット内の複数レポートを上書きで失わない。
- 同じシーケンス番号を新規データとして扱わない。CANへのキュー投入失敗時は更新フラグを保持する。
- NaN、Inf、CAN表現範囲外の値、100 msより古いサンプルは送信しない。
- Set Feature後は非ゼロのGet Feature Responseを待つ。250 msで応答がなければ同じ設定を最大3回送信。その後Get Featureで両設定を再確認し、両センサーの新しい初回レポートを受けてからreadyとする。初期化失敗時は1秒待って再試行する。
- SH-2リセット通知、SPI通信異常、いずれかのレポートが1秒途絶えた場合はデータを破棄し、ハードウェアリセットから再初期化する。
- CAN自動再送を無効化し、ハードウェアの未完了送信は1件に制限する。DARによる送信試行終了を確認したらその要求を解放する。バス待ちなどで要求が未完了のまま残る場合は、古い方のサンプルの計測から100 msでキャンセルを要求し、取消完了まで次を投入しない。BNO異常・再起動時も取消を要求する。既にバス上で送信中のフレームは取消と競合して完了する場合がある。100 msごとにHAL2のBus-Off復帰APIを呼ぶ。
- TIM2を1 MHzの32 bitフリーランニングカウンタとして使い、EXTI0でINT検出時刻を記録する。SH-2へ渡す時刻は1 µs分解能。CANには含めない。
- メイン処理は未処理データがないときWFIで待機する。EXTI・DMA・SysTickで起床し、INTレベル確認も併用して取りこぼしたエッジで停止しない。
- SHTPチャネル番号を配列アクセス前に検査する。SH-2のセンサー／制御／Gyro RVレポートは長さ不足なら破棄する。
- UARTログは1024 byteのリングバッファとTX DMAで非同期出力する。満杯時はログを捨ててカウントし、BNO処理を止めない。通常のセンサ値はUARTへ出力しない。

`can_queued_frames` はCAN FIFOへの受付回数であり、相手による受信完了回数ではない。
`can_sent_frames` はACKを伴う送信完了、`can_expired_frames` はソフトが取消を要求した後の未送信完了を数える。
`can_unsent_frames` はソフトの取消要求なしに終了した未送信試行（DARのACK欠落・通信エラー・調停負けなど）を数える。
UARTのHealthには `queued` と `unsent` を出力し、送信要求・送信成功・失敗を区別する。
`bno_init_failures`、`bno_config_retries`、`bno_recoveries`、`accel_reports`、`gyro_reports`、
`bno_dma_reads`、`bno_dma_writes`、`bno_max_int_latency_us`、`log_dropped_bytes`、`log_dma_errors` もデバッガから確認できる。
INT遅延カウンタはEXTIハンドラで時刻を記録してからCSを下げる直前までのソフトウェア計測であり、ピン波形の測定ではない。

## ビルドとMX2再生成

必要なコマンド: CMake 3.30以上、Ninja、`arm-none-eabi-gcc/g++/objcopy/size`。

```sh
cd stm32/c542rc-bno085
make build
```

生成物:

- `build/firmware/c542rc-bno085.elf`
- `build/firmware/c542rc-bno085.bin`
- `build/firmware/c542rc-bno085.hex`

MX2では `c542rc-bno085.ioc2` を開く。CMake / GCC / Debugで、出力先は `c542rc-bno085_cmake`。
アプリは `App/`、SH-2は `Drivers/sh2/`、CAN codecは `protocols/` に分離している。
`make build` がCMakeのproject hookを渡し、生成された空のmainをアプリのmainに置き換える。
生成コードを直接編集せずに再生成できる。
**生成先だけをそのままビルドすると空のテンプレートmainになるため、必ず上記のMakefileを使う。**

書き込み時は接続先がNUCLEO-C542RCであることを確認し、ELFをSTM32CubeProgrammerで書き込む。
2026-11-06にCubeIDE同梱CubeProgrammer 2.22.0で書き込み・照合を実施した。
この環境のPATH上のCubeProgrammer 2.20.0はST-LINKを検出するがC542のMCU識別に失敗するため、2.22.0を使用する。

## USB-CAN接続後の切り分け（2026-11-06）

USB-CANはCH340として認識。ユーザー確認ではBOOT=OFF、USB-CAN側120Ω=ON、
NUCLEO側JP9装着済み。CAN-H/L接続済みの状態でも、921600 bpsの10秒キャプチャは
生バイト0件で、標準IDのデコード以前に受信できていない。
提供された[ROS 2ブリッジ](https://github.com/ryo-0723/ros2_robstride_usb_can_bridge)は
AT形式・拡張フレーム向けで、アダプターのCAN速度設定を行わない。
シリアル921600 bpsの設定成功はCAN側1 Mbpsの設定確認を意味しない。

実行中のUART診断では、FDCANカーネル144 MHz、NBTP=0x00007c11（1 Mbps）、
PB8/PB9のAF9、PE2出力LOWを確認。一方、CCCR=0x00000001、ECR=0x005d00f8、
PSR=0x000007e5で、バスオフと最終エラーBit 0を観測した。
一時的な20 µsの送信ピンLOW診断でも受信ピンはHIGHのままだった。
これは外部配線または基板の送受信経路を追加確認する根拠であり、故障箇所の確定ではない。
CN18の外部配線を外すと、RXは1→0→1と正常に追従し、TXピンのLOWも確認できた。
この状態ではCCCR=0、ECR=0x00100080、PSR=0x0000076b（ACKエラー、バスオフなし）。
外部接続の有無で症状が変化するため、ケーブルとUSB-CAN側の接続を優先して確認する。
CAN実受信は未達。CANのID・DLC・ペイロード・通信速度は変更していない。

BNOは一度、SPI異常後にジャイロの設定応答が得られなくなった。
MCUリセットでは復旧せず、BNOを含む電源再投入後に両センサーのDMA取得が復旧した。
根本原因は未特定。長時間運転の安定性は引き続き確認が必要。

注意: この環境のCubeProgrammer CLI接続では、切断後にMCUの再起動を観測した。
別々のCLI呼び出しで得たカウンターを、連続稼働の差分として扱わない。
切り分け用のGPIOパルス・レジスター出力は通常アプリから除去済み。
基板接続の根拠: [ST UM3615 §7.11](https://www.st.com/resource/en/user_manual/um3615-stm32c5.pdf)。

CN18の2番・3番を入れ替えたとの連絡後も、10秒間のUSB-CAN受信は0 byte。
同じ診断でTXのLOWを確認したが、RXはHIGHのまま（1/1/1）だった。
CCCR=1、ECR=0x005d00f8、PSR=0x000007e5で、接続時の症状は変わらなかった。
端子位置・ケーブルの対応関係とUSB-CAN側の回路状態は未確定。
この再診断後も、一時診断コードを除去して通常のDMA版に戻した。

続いて1番・3番を入れ替えたとの連絡後は、接続状態でもRXが1→0→1に追従した。
CCCR=0、ECR=0x00100080、PSR=0x0000076bとなり、Bit 0／バスオフは観測されず、
ACKエラーへ変化した。USB-CANの10秒受信はまだ0 byte。
USB-CAN側のエラー状態を解除するため、アダプターのみのUSB再接続を依頼した。

USB-CANのみ電源再投入後も10秒受信は0 byte。通常DMA版の起動後45,158 ms時点で、
BNO初期化失敗・再接続・SHTP異常・SPI異常・UART異常は0、加速度11,567件、
ジャイロ8,944件。CAN受付469件、期限切れ468件、送信完了0件。
USB-CAN側までの端子対応と、アダプター側のCAN速度／動作モードの確認が残る。

## CAN実受信成功（2026-11-06、最終確認）

CAN-H/Lを入れ替えたとの連絡後、通常DMAファームのままUSB-CAN受信に成功した。
CAN仕様（Classic CAN、標準ID 0x100、DLC 8、1 Mbps）は変更していない。

- 10.011秒で33,949 byte、正常フレーム1,997件。受信フレーム間の時刻から約199.6 Hz。
- AT形式のIDフィールドは `00 00 00 04`。既存ロガーのLittle-Endian `(StdId << 18)` 形式に一致。
- 取得区間内のジャイロ連番は全1,996遷移で+1（8 bit wrapを含む）。連番欠落は観測されなかった。
- 加速度連番の差は+1または+2。加速度の報告周期4,000 µsに対しCANは約5,000 µsなので、最新値を使う動作と整合する。
- 実測範囲: 加速度X −0.078125～0.343750 m/s²、Y 0.113281～0.691406 m/s²、ジャイロZ −0.037109～0.060547 rad/s。

この確認は10秒間の受信結果であり、長時間安定性やセンサー精度の校正を保証するものではない。
前節までの受信0件・未達の記述は配線修正前の切り分け履歴。

## ソフトウェア信頼性改良（2026-11-06）

CANのDBC・codec・ID・DLC・1 Mbps設定は変更していない。

- SH-2の計測タイムスタンプとTIM2の現在値を比較し、100 ms以上古いサンプルと未来時刻を除外する。HALのms時刻へ変換する際は経過時間を切り上げ、鮮度を実際より長く見積もらない。TIM2とHAL tickの独立したwraparoundをテスト済み。
- DMA完了とタイムアウトの競合を短い割り込み禁止区間で処理し、HALの転送中止は割り込みを戻してから行う。
- BNO起動時のリセットを一回のLOWパルスに整理。初期化が3回続けて失敗したら再試行を1秒から5秒間隔にし、待機中はWFIを使う。電源を物理的に切る機能はない。
- システム初期化前にIWDGを開始。LSI公称32 kHz、分周128、reload=1999で公称約8秒。メインループだけが更新し、割り込みが動いていてもメイン停止は検出する。オプションバイトは変更しない。
- 起動時にリセット原因、5秒ごとにセンサー件数・精度状態・CAN送信完了/期限切れ・バスオフ回数・最終CANエラー・古い/不正サンプル・再初期化・ログ欠落・スタック余裕をUARTへ出す。CANペイロードへ診断情報は追加しない。精度状態だけを理由に送信を停止する変更も行っていない。
- 実機で追加処理による1 KiBスタック不足を検出。HotPlugでCFSR=0x00100000（STKOF）、HFSR=0x40000000、MSP=__StackLimitを確認。`user_modifiable/Device/STM32C542RCT6/stm32c542xc_flash.ld`のスタックを4 KiBへ変更し、使用量の高水位を監視する。設定テストで容量の退行を検出する。

ウォッチドッグはデバッグ停止中も進む構成。通常版のビルドは`BNO_HARDWARE_SELFTEST=OFF`。
異常注入は別のbuildディレクトリで明示的にONにした場合のみ有効で、
CANトランシーバー待機→復帰、センサーresetイベント、メイン停止を順に行う。
IWDGリセット後は注入せず通常動作し、復旧を確認できる。試験後は必ず通常版へ書き戻す。

macOSでCANとVCPを同時記録する（アダプターへのコマンド送信なし）:

```sh
python3 tools/capture_validation.py --seconds 180 --output build/validation/normal
```

CSV・生CANバイト・UARTログ・JSON統計を保存する。受信時刻はPC時刻であり、
OSとUSBのバッファリングによる揺らぎを含む。センサーの計測周期の直接測定には使わない。

IWDGの根拠: [ST HAL IWDG概要](https://dev.st.com/stm32cube-docs/stm32c5xx-hal-drivers/2.1.0/en/docs/drivers/hal_drivers/iwdg/hal_iwdg_overview.html)。
補足: CubeProgrammerの正しい非リセット接続指定は`mode=HotPlug`。
以前使用した`mode=HOT`は警告の上でNormal接続になり、再起動を起こしていた。

### 改良版の検証結果

- ホストの6系列の検査に成功（codec/サンプル、生成設定、SHTP境界、SH-2境界、CAN取消、SPI DMA）。新たに計測時刻の鮮度判定・未来時刻・TIM2/HAL tickの独立wrap・タイムアウト後の遅延コールバックを検証した。
- 通常版: text=52,912 B、data=128 B、bss=12,280 B（4 KiBスタック等の予約領域を含む）。`BNO_HARDWARE_SELFTEST=OFF`を確認し、通常binにSELFTEST文字列がないことも確認した。
- 最初の60秒受信: 11,976フレーム、約199.59 Hz、ジャイロ連番は全11,975遷移で+1。UARTで再接続・初期化失敗・CANバスオフ・SPI/UARTエラー・古いサンプルの除外・ログ欠落は0。スタック未使用領域の観測最小は3,020 B。
- 異常注入版: PE2を1.5秒HIGHにしてCANバスオフを発生させ、LOWへ戻した後に送信再開を確認。期限切れ取消16件、バスオフ検出1回をログに記録した。
- 同試験でSH-2リセットイベントを模擬し、アプリがBNOの実リセット/再設定を行い、readyとCAN送信へ戻ったことを確認。
- 同試験でメインを意図的に停止（割り込みは継続）させ、IWDGによる再起動、リセット原因IWDG=1、BNO初期化とCAN送信の復帰を確認。PCで観測した最大受信空白は約8.21秒（再起動・センサー起動時間を含む）。

精度状態の観測値は加速度2／ジャイロ0。これは通信成功と測定精度が別であることを示す診断情報であり、
今回の改良で校正設定を変更したり、精度0のデータを自動的に遮断したりはしていない。
電源再投入でしか復帰しないBNO内部状態については、この配線のままソフトで電源を切れないため解決を保証しない。

- 最終通常版の3分受信: 35,921フレーム、約199.55 Hz、不正ATフレーム0、再起動0。36回のHealth記録すべてでonline=1、初期化失敗・再接続・CAN期限切れ/バスオフ・SPI/UART異常・古い/不正サンプル・ログ欠落は0。スタック余裕の最小は3,020 B。
- この3分間でジャイロ連番は+1が35,916回、+2が4回。4サンプル分がCANへ現れなかった。MCU側のジャイロ報告数と送信完了数の増分差とも整合する。従来どおり最新値優先・最短5 ms間隔の送信であり、全センサーレポートを漏れなく配送する仕様ではない。CAN通信エラーや再初期化は同区間では観測されなかった。
- 数時間以上の連続運転・センサー精度校正・実配線の脱着試験はこの最終試験には含まない。

### 精度ステータス0の追加調査

2026-11-06、一時診断で`sh2_getCalConfig()`を実行し、応答成功（status=0）、
mask=0x05（加速度の動的校正ON、ジャイロOFF、磁気ON、平面加速度OFF）を確認した。
現行アプリは校正済みジャイロ出力を要求するが、動的ジャイロ校正の有効化はしていない。
校正設定のON/OFFと出力レポートの精度ステータス0～3は別の情報。
ジャイロ校正OFFはステータス0の原因候補だが、ON時との比較試験は未実施なので
それだけを原因と断定しない。校正設定やDCDは変更せず、通常版へ戻した。

## ジャイロ動的校正の有効化と静止比較（2026-11-06）

ユーザー依頼により、ジャイロの動的校正を起動時とBNO再初期化時に有効化するよう変更。
`Get Cal Config`で現在の設定を読み、`SH2_CAL_GYRO`だけを追加して`Set Cal Config`を実行し、
読み戻しが要求値に一致した場合に取得を開始する。実機でmask=0x05→0x07を確認。
CANのID・DLC・1 Mbps・符号・スケール・フィールド配置・5 ms最短送信間隔は変更していない。
DCDを明示的に保存するコマンドは追加していない。

他の校正設定を保持するため、SH-2の`getCalConfigRx()`で従来読み落としていたR5（On Table Cal Enable）も復元するよう修正。
公式SH-2仕様Figure 58に対応し、5つのenableビットの全32組合せをホストテストで検証。
この実機のR5は0だったため、設定は0x05→0x07となった。
精度状態が変わったときだけ、時刻と状態およびZ軸Q9値をUARTログへ出す。

ユーザーが机上で静止させた状態で、OFFの60秒、次にON版へ書き込み後の120秒を記録。
ゼロ点比較はOFFの全60秒とON記録の最後の60秒を使用し、どちらも11,973フレーム。
再起動を挟んだ前後比較であり、温度・微振動等を統制した精密な校正試験ではない。

| CANのZ軸出力 | 動的校正OFF | 動的校正ON |
|---|---:|---:|
| 精度ステータス | 0 | 3 |
| 平均 [rad/s] | +3.5888e-6 | +1.6313e-7 |
| 標準偏差 [rad/s] | 0.00059575 | 0.00057091 |
| ちょうどゼロの割合 | 98.5718% | 98.6553% |
| 受信頻度 [Hz] | 199.542 | 199.542 |

ON版は起動後286 msの最初のジャイロ報告でstatus=3となり、以後のHealth記録でも3を維持した。
起動・SPI・UART・CAN異常、古いサンプル除外、再接続、ログ欠落は観測されなかった。
スタック未使用領域は最小2,492 B。ホストの6系列検査とCAN仕様一致検査を通過し、書き込み照合済み。

OFF時から静止Z出力がほぼゼロだったため、今回の結果でゼロ点精度が大幅に改善したとはいえない。
1サンプルの分解能は1/512=0.001953125 rad/s。上記の小さな平均値は多数サンプルの平均であり、
その桁まで絶対精度を保証する値ではない。確認できた主な変化は精度ステータス0→3。
実動作中、特にゆっくりした回転での動的校正の影響は別の評価項目。

[SH-2仕様 §6.4.6](https://www.ceva-ip.com/wp-content/uploads/SH-2-Reference-Manual.pdf#page=53)、
[BNO08x校正の説明 §3.1.3–3.1.6](https://www.ceva-ip.com/wp-content/uploads/BNO080_085-Datasheet.pdf#page=38)。

## 最新値の単発送信への変更（2026-11-07）

ユーザー依頼でFDCANの自動再送を無効化（DAR）した。CubeMX設定と生成済み設定を同期し、
DBC/codec・標準ID 0x100・DLC 8・1 Mbps・最短5 ms間隔は維持。送信失敗後はハードウェアの
pending解除を確認して次の最新値へ進む。ソフト側の期限切れ取消とDARの未送信完了を別々に計数する。
ACK欠落自体は解消せず、調停負け・通信エラーでも同じデータは再送しない。

- ホストの全6系列の検査に成功。DAR設定の検査と、単発送信失敗後に100 msを待たず次の5 ms枠で送信要求できるテストを追加。
- ビルド成功（text=54,176 B、data=128 B、bss=12,296 B）。STM32CubeProgrammerで実機書き込み・照合済み。
- 他のCANデバイスを起動したまま30秒受信し、IMUは5,280フレーム、平均約176.0 Hz。アダプターのタイムスタンプによる受信間隔は中央値4.992 ms、平均5.681 ms、95パーセンタイル9.984 ms、最大39.978 ms。
- ジャイロ連番は+1が4,614回、+2が628回、+3が36回、+8が1回。連番から707サンプル分の欠落を観測した。欠落箇所はこの測定だけでは特定できない。
- UARTの25,000〜50,001 msでは送信受付が4,990回増加（約199.6 Hz）。ACK付き送信完了は0、期限切れ取消0、ACKエラー継続。取得・単発送信要求は進むが、正常なCAN送信成功としては扱えない。
- 同じ診断区間で初期化失敗・再接続・SPI/UART異常・ログ欠落は0。スタック余裕は2,476 B。
- 測定ログはリポジトリ外の一時領域に保存。約100 msの再送待ちは解消したが、バスの通信不良や受信欠落は未解決。

ACKエラーは「STM32がACKを認識できなかった」という観測であり、ROBSTRIDE・VESC・USB-CANが
ACKを送出しなかったと断定するものではない。相手機器の動作状態、ビットタイミング、物理配線、
STM32側の受信経路を含む原因の切り分けは未完了。

その後のUSB1給電への切替時にCANデータが停止した件では、ユーザーがA3→PS0/WAKE線の抜けを発見し、
接続修正後の動作復旧を確認した。これはユーザーによる確認であり、復旧後のACK状態・受信周期は再測定していない。
